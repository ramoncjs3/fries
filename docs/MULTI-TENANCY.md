# 多租户方案

> **这份文档推翻了 fries 原来的一条核心边界。** DECISIONS.md §0 原文是「不做多租户、
> 不做 i18n、不做 SaaS」，§9 也把多租户列在「明确不做」里。现在改为**做多租户**，
> i18n 和其它「不做」项保持不变。
>
> 单独成文而不是塞进 DECISIONS.md，是因为它横切数据、认证、授权、审计四层，
> 塞进任何一节都不合适；插一个新章节又会打乱既有章节号（`make lint-docs` 靠章节号做校验）。

## 0. 定位怎么变了

| | 原来 | 现在 |
|---|---|---|
| 使用规模 | 10 人以内**单个**内部团队 | 一次部署，**多家公司**各自注册使用 |
| 部署 | 单机 compose，一套数据服务一个组织 | 单机 compose，一套数据服务 N 个组织 |
| 头号安全风险 | 越权（普通用户干管理员的事） | **跨租户**（A 公司看到 B 公司的数据） |

第三行是最要紧的变化。越权顶多是内部人多看了点东西；跨租户泄露是**直接的客户事故**，
一次就足够让产品死掉。

所以整套设计围着一个目标转：**让「漏写一个 `WHERE tenant_id = ?`」这件事根本发生不了。**

⚠️ 注意措辞 —— 不是「发生了也不要紧」。评估过能兜底的方案（数据库 RLS）之后没有选它
（理由见 §1.1），所以**这里没有第二道防线**：目标只能是在写代码那一刻就堵死，
而不是出事之后拦住。§1.2 那四层机械强制就是为此存在的。

## 1. 隔离方案：共享表 + `tenant_id`，**应用层强制**

一个库、一套表，每行带 `tenant_id`，**每条查询自己带上租户条件**。

选它而不选「一租户一 schema」或「一租户一库」，理由是三条叠加：

1. **不堵死后路。** 将来真来了要求数据物理独立的大客户，把整套系统再部署一份就是
   「一租户一库」—— 这条路本来就通，不需要现在为它付代价。而「一租户一 schema」是唯一
   一个「现在贵、将来还得换」的选项：租户一多它两头不讨好，隔离没强到独立库，
   扩展性还比共享表差。
2. **迁移是原子的。** 一租户一 schema 的迁移要跑 N 遍且不是原子的 —— 跑一半失败就是
   「部分租户新版、部分租户旧版」，一个人维护的项目扛不住这种状态。
3. **和业界主流一致。** 绝大多数 SaaS 就是这么做的（Rails 的 `acts_as_tenant`、
   Django 的自定义 Manager、Hibernate filters 都是同一个思路）。

### 1.1 ⚠️ 为什么不用 PostgreSQL 行级安全（RLS）—— 以及代价

评估过 RLS（在数据库层强制隔离，应用漏写条件也泄露不了），**最终没选它**。

不选的理由是**它会把失败变成静默的**：忘了设租户上下文时，每条查询返回 0 行 ——
页面空白、列表没数据，但没有任何报错，得反推半天。而应用层强制**做对了**的话，
漏传租户是编译错误，当场就知道。附带代价还有一串：三个数据库角色、所有请求包事务
（连接被握住整个请求周期）、迁移顺序约束、一张「允许绕过」的旁路清单。

⚠️ **「做对了」三个字是有分量的**：应用层默认**不会**给你编译错误（Go 有零值，
见 §1.2 开头那段）。只有把 §1.2 ① 那套 `internal` 包收紧做出来，「漏了编译不过」
才成立。**换句话说，不选 RLS 的理由本身就依赖 §1.2 落地** —— 这也是为什么
下面反复强调它不是可选项。

**但要清醒地记住不选它的代价：没有兜底网。**

> **一条漏写的 `WHERE tenant_id = ?` 就是一次跨租户泄露，没有第二道防线。**

代码由 AI 逐次生成，这个风险不是理论上的。所以下面 §1.2 那套机械检查**不是可选项** ——
它是这个方案里唯一顶替兜底网的东西，砍了它这个方案就不成立。

### 1.2 应用层怎么做到「机械强制」而不是靠自觉

Go 里**没有 Rails 的 `default_scope`、也没有 Django 的自定义 Manager** ——
sqlc 生成的就是一堆普通函数，没有地方挂钩子。所以要靠四层，缺一不可。

#### ⚠️ 先说一个不成立的想法：「参数里有 TenantID 字段，漏了编译不过」

**不成立。** Go 有零值：`ListUsersParams{Keyword: x}` 少填 `TenantID` 照样编译通过，
跑出来是 `uuid.Nil`，查到 0 行 —— **和 RLS 的静默失败一模一样**。
「结构体里有这个字段」不等于「必须填」。

真正的办法是让业务代码**根本碰不到那个字段**。

#### ① 生成一层租户绑定的 `Queries` 包装 ← 这是核心

```go
q := repo.ForTenant(tenantID)          // 拿句柄的唯一入口
rows, err := q.ListUsers(ctx, repo.ListUsersArgs{Keyword: kw})   // 没有 TenantID 这个字段
```

包装层自己把 `TenantID` 填进底层的 params。业务代码**填不了也漏不了** ——
它看到的参数结构里压根没有这一项。

**用 Go 的 `internal` 包规则把「绕过」这条路堵死**：sqlc 的生成物挪到
`internal/repo/internal/sqlcgen/`。Go 规定 `internal` 下的包**只能被它父目录那棵树
import** —— 也就是只有 `internal/repo/...` 碰得到。业务代码（service、handler）
**在编译期就拿不到不带租户的句柄**，不是「不该用」，是「用不了」。

这是 Go 里能拿到的最强保证，比中间件强得多 —— 中间件只能拒绝请求，
包可见性能拒绝**编译**。

包装层由 `cmd/gen` 生成（sqlc 的产物是固定格式，好解析），**不手写** ——
手写一遍几十个查询，迟早有一个忘了注入。

#### ② 中间件：负责「没有租户就拒绝」，不负责注入条件

认证之后把 `tenant_id` 放进 ctx，并且提供 `MustTenant(ctx)` —— ctx 里没有就报错，
**不是放行**。这和现有的 `authz.MustScope` 是同一个范式（DECISIONS.md §3.3
「repo 层默认拒绝」），照抄即可。

⚠️ **别指望中间件能拦住漏写租户条件的查询** —— 它看不见 SQL。
它的职责就两条：把租户放进 ctx、没有租户的请求直接 403（登录和健康检查走白名单）。

#### ③ SQL 静态检查：每条查询必须带 `tenant_id`

解析 `backend/db/queries/*.sql`，凡是碰了租户表的 `SELECT` / `UPDATE` / `DELETE`，
条件里必须出现 `tenant_id`；`INSERT` 的列里必须有 `tenant_id`。不满足就**构建失败**。

①保证「调用方填了」，③保证「SQL 里真的用了」—— 两件不同的事，都要查。
纯静态、不连库、秒级，进 `make dev-check`。豁免写在白名单里并注明理由
（目前只有 §8.1 那三张认证表）。

#### ④ 每个模块一条跨租户测试

种两个租户的数据，调模块的 List/Get，断言看不到对方的。生成器为每个模块自动产出
（和现有的「不带 scope 调 List 必须报错」是同一个手法，DECISIONS.md §3.7）。

#### 这套机制的缺口在哪

**手写代码。** 登录、导出、AI 工具、跨模块统计这些「没有生成器兜底」的路径
（AGENTS.md 路由表里明确列着）：③能查到它们用的 SQL，①能管住走 repo 的调用，
但**代码里怎么用查询结果**查不到 —— 比如把两个租户的数据在内存里拼一起。

这些路径的 review 要格外仔细，每条都要有自己的跨租户测试。**这就是不用 RLS 的代价，
认了就要认到底。**

### 1.3 评估过、但没选的两个方案

写下来是为了**不用再纠结第二次**。

| 方案 | 它强在哪 | 为什么没选 |
|---|---|---|
| **PostgreSQL RLS** | 数据库层强制，应用漏写条件也泄露不了 | 失败是**静默的**（漏设上下文 = 查询返回 0 行，无报错）；附带三个数据库角色、所有请求包事务、迁移顺序约束、旁路清单，对一人维护的项目过重 |
| **换成 ent（ORM）** | Privacy 层写一次、所有生成的 builder 自动过滤，17k star 生态成熟 | ⚠️ **它的 privacy 管不住裸 SQL** —— ent 官方文档明说 `ExecContext`/`QueryContext` 执行的语句不走 ent，会跳过 hooks、privacy、validators。而本项目必须用裸 SQL 的地方不少（部门递归 CTE、审计分区表、将来的导出统计），**缺口和 sqlc 方案是同一个**。既然缺口一样，为它重写 repo 层和四个模块不划算 |

⚠️ ent 的**迁移**其实不冲突（versioned migrations 能输出 goose 格式，触发器和分区表继续手写）
—— 这条本来以为是死结，查过不是。所以将来若真要换，卡点不在迁移，在「值不值得重写」。

**如果这个项目还在第 ① 步、还没有四个跑通的模块，ent 是更好的默认选择。**

## 2. 数据模型

### 2.1 新增表

| 表 | 说明 |
|---|---|
| `tenants` | 租户本身。**没有 `tenant_id`**，它是平台级的 |
| `platform_admins` | 平台管理员。**独立于 `users`**，见 §2.3 |

`tenants` 的关键字段：`code`（登录时输入的公司代码，**全平台唯一**）、`name`、
`status`（`active` / `suspended`）。

### 2.2 既有表全部加 `tenant_id`

`users` `roles` `role_permissions` `user_roles` `sessions` `service_accounts`
`settings` `departments` 加 `tenant_id uuid NOT NULL`。

⚠️ **`audit_logs` 是例外，它的 `tenant_id` 可空** —— 未认证请求（登录失败、健康检查）
也要写审计，那些记录没有租户。理由见 §7.2。查询审计时**必须显式带上租户条件**，
NULL 的那些只有平台端看得到。

两家公司都想要一个叫 `admin` 的账号，所以唯一约束基本都要改成租户内唯一。
**但不是全部** —— 下面这张表是对着 `backend/db/migrations/` 里的真实索引一条条核过的：

| 现有索引 | 怎么改 | 为什么 |
|---|---|---|
| `uk_users_username` | `(tenant_id, username)` | |
| `uk_users_email`（`lower(email)` 函数索引） | `(tenant_id, lower(email))` | 别漏了 `lower()` |
| `uk_users_phone` | `(tenant_id, phone)` | |
| `uk_roles_key` | `(tenant_id, key)` | |
| `uk_departments_code` | `(tenant_id, code)` | |
| `uk_departments_sibling_name` | 加 `tenant_id` | |
| `uk_departments_root_name`（`parent_id IS NULL` 的那条） | 加 `tenant_id` | 根节点的 NULL 父级在唯一索引里互不相等，所以单独一条 |
| `uk_service_accounts_name` | `(tenant_id, name)` | |
| **`uk_sessions_token`** | **保持全平台唯一，不加 `tenant_id`** | ⚠️ 见下 |
| **`uk_service_accounts_prefix`** | **保持全平台唯一，不加 `tenant_id`** | ⚠️ 见下 |

⚠️ **最后两条不能改，改了认证就废了。** 验证会话是「拿 cookie 里的 token 去查是哪个人」，
那一刻还不知道租户是谁；API Key 同理。这两个值必须能**在不知道租户的前提下**唯一定位到
一行，查出来的那一行再告诉我们 `tenant_id`。详见 §3.2 ③ —— **认证发生在租户上下文建立之前**，
这是整个方案里绕不开的一处特殊。

### 2.2.1 跨租户外键：真正危险的是这两条

`created_by` 这类列**现在根本没有外键**（查过了，就是裸的 uuid），所以那里没有约束可加。
真实存在的外键有六行（**七条** —— `user_roles` 那一行是两条），其中两条一旦跨租户会直接出事：

| 外键 | 跨租户的后果 |
|---|---|
| **`departments.parent_id` → `departments.id`** | 把部门挂到别家公司的部门下面，**整棵树结构被污染** |
| **`users.department_id` → `departments.id`** | 把人分到别家公司的部门里 |
| `user_roles.user_id` / `role_id` | 给本租户的人绑别家的角色 |
| `role_permissions.role_id` | |
| `sessions.user_id` | |
| `service_accounts.role_id` | |

全部改成**复合外键**，在数据库层杜绝：

```sql
FOREIGN KEY (tenant_id, parent_id) REFERENCES departments (tenant_id, id)
```

代价是被引用的表要加 `(tenant_id, id)` 唯一索引。值得 —— 这类脏数据一旦写进去，
页面上会表现成「部门凭空消失」「这个人的部门查不到」，排查时极难联想到是跨租户。

### 2.3 平台管理员为什么是独立的表

不在 `users` 上加一个 `is_platform_admin` 就完事，是因为平台管理员**不属于任何租户**。
塞进 `users` 就得让 `tenant_id` 可空 —— 而 `tenant_id` 可空会毁掉整套强制机制：
`ForTenant` 包装注入的条件对 NULL 行永远不匹配，于是每处查平台管理员的地方都要开特例，
而「租户内的用户列表」又要处处记得排掉它们。**漏一处就是把平台管理员暴露给客户。**

两种主体的权限体系本来也不一样。分成两张表，两边都干净，`users.tenant_id` 也能保持
`NOT NULL` —— 这条对 §1.2 的机械强制很要紧。

### 2.4 审计

`audit_logs` 加 `tenant_id`，分区仍然按月。

**哈希链按租户各走一条。** `audit_chain_head` 现在是一张**单行表**
（`only_row boolean PRIMARY KEY CHECK (only_row)`，靠 CHECK 保证只有一行），
改成每租户一行要动三处：主键换成 `tenant_id`、去掉 `only_row` 那套单行约束、
**改触发器函数 `audit_chain()` 按 `NEW.tenant_id` 取对应的链头**。

⚠️ 触发器里**必须用 `NEW.tenant_id`**，不能用任何「当前租户」的概念 ——
审计行是触发器代写的，它唯一可信的租户来源就是那一行自己带的值。
（那个触发器是 `SECURITY DEFINER`，让应用账号在没有 `audit_chain_head` 写权限的情况下
也能插审计，这一点不用改。）

共用一条链的话，验证 A 租户的完整性要读到 B 租户的记录，既慢又不该。

平台管理员的操作也要审计，记在**平台级审计**里（`tenant_id` 为空的那批，
或单独一张表 —— 实现时定）。

## 3. 授权与权限 ⚠️ SaaS 下这是重中之重

### 3.1 Casbin 换成带 domain 的模型

现在整个进程只有一个 Casbin enforcer，角色 key 是全局的。两家公司各有一个 `admin`
角色，在策略里会直接撞车。

换成 Casbin **官方的 RBAC with domains** 模型，`domain` 就是 `tenant_id`：

```
[request_definition]  r = sub, dom, obj, act
[policy_definition]   p = sub, dom, obj, act
[role_definition]     g = _, _, _
[policy_effect]       e = some(where (p.eft == allow))
[matchers]            m = g(r.sub, p.sub, r.dom) && r.dom == p.dom \
                          && (p.obj == "*" || r.obj == p.obj) \
                          && (p.act == "*" || r.act == p.act)
```

🔴 **`(p.obj == "*" || ...)` 这两段不能丢。** 现有模型（`authz/checker.go` 的
`casbinModel`）里就有它们 —— 内置 admin 角色的策略是一条 `*:*`，靠的正是这个通配匹配。
照搬 Casbin 官网那份 domain 示例（它用的是 `r.obj == p.obj`）会**当场让所有租户的
管理员失去全部权限**，而且现象是「登录进去什么菜单都没有」，很难第一时间联想到匹配器。

**用官方模型，不自己在 key 前面拼租户前缀** —— 拼字符串这种方案迟早会在某个忘了拼的
地方漏掉，而 domain 是 Casbin 匹配器的一等公民。

### 3.2 对着 DECISIONS.md §3 逐条过一遍

原来的权限模型是给**单个组织**设计的，直接搬到 SaaS 上**有九处会出事**。按严重程度排：

#### ① 「最后一个管理员」的护栏会跨租户失效 —— 会锁死客户

DECISIONS.md §3.5.1 第三条：「最后一个可用的超级管理员不能停用、不能删除、不能被摘掉角色」。
**核过实现了**：`CountActiveAdmins`（`backend/db/queries/user.sql`）是一条
不带任何租户条件的全表 count。多租户下这就错了：
A 公司还有 admin，B 公司删掉自己最后一个 admin 时检查照样通过 —— **B 公司被锁在门外**，
只能上数据库救。

**三条兜底全部要改成「每租户一份」**：

| 护栏 | 改成 |
|---|---|
| 内置 `admin` 角色不可改不可删 | **每个租户各有一个**自己的内置 admin 角色，开租户时一并建 |
| 通配 `*:*` 只保留给内置 admin | 判断限定在本租户内 |
| 最后一个超级管理员不可停用/删除/摘角色 | **查询必须带 `tenant_id`** |

#### ② 平台权限点会混进租户的角色配置页 —— 租户能给自己勾「开租户」

`perm.Module` 的 key 是全局的，角色配置页的勾选树直接吐整个注册表（DECISIONS.md §3.7 就是这么设计的，
好处是不会漏）。平台管理端的模块（开租户、停租户）一旦注册进同一张表，
**租户管理员在自己的角色页上就能看到并勾上它们**。

`perm.Module` 加一个 `Realm` 字段（`tenant` / `platform`）：

- 角色配置页只吐 `Realm: tenant` 的
- 平台端只认 `Realm: platform` 的
- **启动自检加一条**：任何租户角色里出现 `platform` 权限点，服务直接启动失败

#### ③ 认证发生在租户上下文建立**之前** —— 三张表只能靠自觉

`ForTenant` 要拿到 `tenant_id` 才能用，而这个值来自会话。但**验证会话本身就要查
`sessions` 表** —— 那一刻还不知道租户是谁。API Key 同理（先查 `service_accounts`
才知道 key 属于谁），登录同理（先按公司代码查 `tenants`）。

**这三张表只能用不带租户条件的查询**，因此：

| 表 | 怎么查 | 保证靠什么 |
|---|---|---|
| `sessions` | 按 `token_hash` 精确查一行 | token 全平台唯一且不可猜 |
| `service_accounts` | 按 `key_prefix` 精确查一行 | 同上 |
| `tenants` | 按 `code` 精确查一行 | 见 §8.1 |

**硬规矩：这三张表只允许「按唯一键精确查一行」，不允许任何列表查询、不允许模糊匹配。**
它们是 §1.2 ③ 那条静态检查的**豁免名单**，豁免要显式写在白名单里并注明理由。

⚠️ 这是**整套方案里唯一一处只能靠代码自觉的地方** —— 三张表，实现时逐条单独 review，
而且**清单只有这三张，加第四张必须专门讨论**。

**另一类是「压根没有 tenant_id」的 infra 表**（和上面三张不同 —— 那三张有 tenant_id、只是某条查询按唯一键先定位）：
`idempotency_keys`、`rate_limits`、`pending_registrations`。它们是「租户之前 / 跨租户」的基础设施
（幂等键的租户拼在 key 里、限流维度拼在 key 里、自助注册发生在建租户之前），本来就没有租户维度。
碰它们的查询走 `Unscoped` + `-- tenant-exempt`，用它们的包（如 `internal/service/registration`）
登记在 `cmd/gen/lintsql.go` 的 `unscopedCallers` 白名单里并注明理由。B1 检查器也会盯着：
有 `tenant_id` 列却没登记进 `tenantTables` 会当场红灯，所以「无租户 infra 表」和「漏登记的租户表」不会混。

#### ④ `data_scope` 的「全部数据」现在有歧义

`all` 的含义从「全部数据」变成「**本租户内**的全部数据」。租户是**硬边界，不是一档 scope**：

- `data_scope` 是**可配置的**（角色上选 all / self）
- `tenant_id` 是**不可配置的**，任何角色、任何 scope 都跨不过去

文档和界面文案都要改口径，否则下一个人会以为 `all` 是真·全部。
**角色页上的「全部数据」要改成「本组织全部数据」。**

#### ⑤ 「拿到 `user:update` 就能自我提权」这条已知边界，上限必须钉死

DECISIONS.md §3.5 承认了一个边界：能改用户角色 = 能把自己提成管理员。单个组织内部这可以接受
（10 个人互相认识，且有审计）。

**SaaS 下它仍然可以接受，但上限必须是「本租户 admin」，永远够不到平台管理员。**
这不是自然成立的，要靠 ② 的 Realm 隔离 + 平台管理员在另一张表来保证，并且要有测试：
**租户管理员用尽一切办法都拿不到平台权限。**

#### ⑥ 审计「给管理员看全」的措辞现在危险

MODULES.md 里写着审计「数据权限不参与（`Scoped: false`）—— 审计就是要给管理员看全的」。
多租户下**「看全」只能是「看全本租户」**。

⚠️ **这句话现在是危险的**：没有 RLS 兜底，照着它写出一条不带租户条件的审计查询，
就是把所有客户的操作记录端给一个人看。措辞必须改，而且审计的查询要走
和别的模块一样的 `ForTenant`（`tenant_id IS NULL` 的平台级记录只有平台端能查）。

#### ⑦ 幂等键和限流缺租户维度

两个都默认在内存里，租户维度靠**把租户拼进 key**解决（不是加表约束）。
多副本部署时可切成 PG 实现（`server.shared_state_store: postgres`，见 SCALING.md §1），
表 `idempotency_keys` / `rate_limits` 没有 tenant_id、维度已在 key 里，属上面 ③ 说的 infra 表。

- **幂等键**的 key = `租户/主体 + 方法 + 路由 + 客户端给的键`（`middleware/idempotency.go` 的 `scopeOf`）。
  不带租户的话，A 租户用过的 key、B 租户再用会被当成重复请求 —— **跨租户干扰**。现在租户已拼进 key。
- **限流**按 IP、用 `golang.org/x/time/rate` 存在内存里（`middleware/ratelimit.go`）。
  ⚠️ 但**限流中间件跑在认证之前**，那时还不知道租户，所以「按租户分桶」对未登录请求
  根本做不到。准确的说法是：**登录之后按租户分桶，登录接口本身只能按 IP + 公司代码**。
  后者尤其要紧 —— 不限的话登录接口就是免费的公司代码枚举器。

  **✅ 两条都已落地**（§15.8）：登录节流带公司代码那一维在 `auth/guard.go`；
  按租户分桶的限流是**另一个** `RateLimiter` 实例，挂在 `Authenticate` **之后**
  （挂在之前的话主体是空的，键永远是空串 —— 等于没装，而且不报错）。
  ⚠️ 租户那一维的阈值故意定得宽：组织内部共用一个桶，太紧就变成同事之间互相挤，
  和公司代码那一维一样会变成针对客户的可用性问题。

#### ⑧ 防漏配要加一条：**新查询忘了带 `tenant_id`**

DECISIONS.md §3.7 的哲学是「防漏配不靠自觉」。多租户下最致命的漏配是
**新写的查询没带租户条件** —— 那条查询就是跨租户裸奔，而且**测试很可能照样绿**
（见下面那条陷阱）。

这件事**可以机械检查**，就是 §1.2 ③ 那条 SQL 静态检查。它是这个方案里
唯一替代 RLS 兜底的机制，**必须做，而且要进 `make dev-check`**。

⚠️ **跨租户测试有个陷阱**：只种一个租户的数据时，「不带租户条件」的查询照样返回正确结果，
测试是绿的。**所以隔离测试里两个租户都必须有数据**，而且断言的是
「A 查到的条数 == A 自己的条数」，不是「A 查到的 > 0」。生成器产出的模板要写死这一点。

#### ⑨ 跨租户外键引用要在数据库层杜绝

现有六条外键全部要改成复合外键，**清单和后果见 §2.2.1**。
最危险的是 `departments.parent_id` 和 `users.department_id` —— 跨租户会把树结构污染掉。

⚠️ 我一开始拿 `created_by` 举例，核过代码后发现**那些列根本没有外键**，是裸的 uuid。
所以那里没有约束可加，只能靠应用层；真正能在数据库层堵死的是那六条。

## 4. 认证

### 4.1 登录要先知道是哪个租户

登录页加一个「**公司代码**」输入框（对应 `tenants.code`）。流程：
公司代码 → 查到 `tenant_id` → **在该租户内**按用户名/邮箱/手机号找人 → 验密码。

⚠️ **公司代码不存在、账号不存在、密码错误，三种情况必须给完全一样的回应。**
否则登录页就成了「这家公司是不是你们客户」的探针 —— 这是既有的「先验密码再看账号状态」
那条规矩（MEMORY.md）的延伸，同一个道理。

⚠️ **「一样的回应」还包括一样的耗时。** 现有代码在用户不存在时会跑一次
`VerifyPassword(in.Password, dummyHash)` 专门抹平时间差（`auth/service.go`）。
新增的「公司代码不存在」如果直接 return，就**重新开了一个时序侧信道** ——
密码哈希是几十毫秒级的，差异肉眼可测。**公司代码查不到时也要走那次假哈希再返回。**

⚠️ **不许提供「检查公司代码是否存在」的接口。** 前端为了体验常会想在失焦时校验一下 ——
那是个免费的客户名单枚举器，比登录接口还好刷（不用密码、不触发账号锁定）。

租户 `suspended` 时同样不能泄露，先验完密码再说「该组织已停用」。

### 4.2 会话

`sessions` 加 `tenant_id`，会话里带上；每个请求从会话取出来，喂给 `repo` 包的 `ForTenant()`
（§1.2 ①）和 Casbin 的 domain（§3.1）。

**绝不接受从请求参数、请求头或前端状态里取 `tenant_id`** —— 那等于把隔离交给客户端，
改一个参数就能读别人的数据。租户的**唯一来源是会话**。

## 5. 开通与邀请：分两步

**第一步（本轮）：平台开通 + 租户内邀请**

平台管理员在平台管理界面开租户 → 系统生成该租户的第一个管理员账号和**一次性初始密码**
→ 平台管理员把凭据交给客户 → 客户管理员登录后在自己租户里新建成员。

「租户内新建成员」这条链路**现在就有了**，就是用户管理的新建（初始密码只显示一次、
强制首次登录改密）。所以这一步几乎不用为「邀请」写新东西。

**为什么先做邀请、后做自助注册**：自助注册必须有邮箱验证，否则垃圾租户会涌进来；
而邮箱验证要发信。**发信能力现在已经有了**（`internal/notify` 的 `Mailer` 接口 + AWS SES，
见 MODULES.md），所以自助注册的前置依赖已扫清，剩下的是它自己那套流程 + 平台开关。
而「一次性凭据由管理员转交」这条路零依赖，项目里早就有这个模式了，所以先做它。

**第二步（发信能力已就绪，可以做了）**：平台设置里加「允许自助注册」开关，打开即是注册即用。
第一步做的东西一点不会白做 —— 邀请链路两种模式都要。

## 6. 平台管理端

独立路由前缀 `/platform`，**独立登录**（`platform_admins`）。这一轮的功能：

- 租户列表（名称、公司代码、状态、人数、创建时间）
- 开租户：填名称和公司代码 → 生成初始管理员 + 一次性凭据
- 停用 / 启用租户

权限上这一轮不做细粒度：平台管理员即全权。真需要分权时再按 `perm` 那套加。

**平台端的查询天然是跨租户的**，走不了 `ForTenant`。所以：

- 平台端**只允许碰 `tenants` / `platform_admins` / `platform_settings` 这三张平台级表**
- ⚠️ 「租户列表要显示人数」是个例外 —— 那要 `count(users) group by tenant_id`。
  **不要为它开一条跨租户查业务表的口子**，而是在 `tenants` 上冗余一个 `user_count`，
  建/删用户时维护。冗余一个数字，比开一条「平台端能查所有租户业务数据」的通道便宜得多
- 将来真需要跨租户查（用量看板），那条路径要**单独一组 SQL 文件 + 单独审计**，
  不和业务查询混在一起

⚠️ **平台端的路由要在 `MustTenant` 的白名单里** —— 平台管理员没有租户，
不放行的话整个 `/platform` 会被自己的中间件拦死。


## 7. 之前漏掉的几块 ⚠️ 都是核过代码才发现的

### 7.1 审计的 `tenant_id` **不能** NOT NULL

审计中间件对未认证请求写的是 `ActorAnonymous`（登录失败、健康检查、直接打接口都会写）。
这些请求**没有租户**，`NOT NULL` 会让它们插不进去。

**`audit_logs.tenant_id` 必须可空**，NULL 表示「平台级 / 无租户」事件。
租户查审计时**显式带上 `tenant_id = ?`**，NULL 的那些自然看不到；平台端才查得到。

⚠️ 有个细节别做错：**公司代码有效、密码错误**的登录失败，应该记在**那个租户名下**，
客户才能看到「有人在爆破我们的账号」。只有公司代码本身无效时才记 NULL。

### 7.2 配置是**进程级单例缓存**，密码策略没法按租户走

`config.Settings` 是「读走全局缓存、写走 DB → 触发器 NOTIFY → 所有实例刷新」
（DECISIONS.md §5）。而 `auth/service.go` 登录和改密时调的 `s.settings.Security()`
拿的是**全局唯一**的一份密码策略。

多租户下密码策略显然该是租户级的（每家公司自己定）。缓存结构要从
「一份 Security」变成「按租户一份」，`Reload` 也要跟着改。

同时要把设置**分成两类**，否则会乱：

| 类别 | 例子 | 存哪 |
|---|---|---|
| 平台级 | 是否允许自助注册、全局限流阈值 | `platform_settings`，只有平台管理员能改 |
| 租户级 | 密码策略、会话超时 | `settings`，主键 `(tenant_id, key)` |

### 7.3 测试基建要改

- `truncatedTables` 要加 `tenants`（MEMORY.md 记过：漏表 = 单独跑过、一起跑就挂）。
- **`builtinRoleSQL` 那段种子写死了一个固定 UUID 的全局 admin 角色**，多租户下
  每个租户各有一个内置 admin，这段要重写成「按租户建」。
- 每个用例要有租户 fixture，且**每个模块至少一条两租户的隔离测试**（§1.2 ③）。

### 7.4 前端的影响面（之前一次没提）

| 改动 | 说明 |
|---|---|
| 登录页加「公司代码」 | 现在只有 `account` + `password` 两个字段。**记在 `localStorage`**，别让人每次敲 —— 它不是凭据，不违反红线 #10 |
| `/me` 要带租户信息 | 侧栏/顶栏要显示「当前是哪家公司」，否则多租户下人会迷路 |
| 平台端是**另一套登录和外壳** | 同一个前端应用，`/platform/*` 走独立的 AuthGate 和菜单源 |
| 角色页文案 | 「全部数据」→「本组织全部数据」（DECISIONS.md §3.3） |
| 生成器的前端模板 | 页面不需要感知租户（后端注入），但**登录/权限相关的模板要改** |

### 7.5 数据迁移的顺序

goose 迁移分三步：

1. 加 `tenant_id uuid`（**可空**）
2. 建默认租户，把现有行全部回填成它
3. 改成 `NOT NULL`、建复合唯一索引、建复合外键

第 2 步之前就设 NOT NULL 会直接失败（已有行没值）。
**本地库直接重建更省事**，这套顺序主要是给将来真有生产数据时用的。

### 7.6 还要加的错误码

`tenant.not_found` / `tenant.suspended` / `tenant.code_taken` / `platform.forbidden`。
⚠️ 登录链路上**前两个不能直接返回给前端**（§4.1：三种失败必须给一样的回应），
它们只进日志和审计。

## 8. 模拟一遍「做完之后」会撞上什么

把方案当成已经实现了，跑几条真实路径。

### 8.1 `tenants` 表自己就是你的客户名单

登录要用公司代码查 `tenants`。**任何一条能列举 `tenants` 的代码路径，
都是在泄露你的客户名单。**

规矩：`tenants` 只允许**按 code 精确查一行**，不提供任何列表查询给租户侧。
列租户是平台端的事（§6）。它和 §3.2 ③ 的两张认证表是同一类，
一起构成 §1.2 ③ 静态检查的**豁免名单**：`sessions`、`service_accounts`、`tenants`。
**就这三张，多一张都要单独讨论。**

### 8.2 租户停用对**已登录的会话**不起作用

把租户改成 `suspended` 之后，已经登录的人**照样能用到 cookie 过期** ——
因为停用只拦登录那一步。

停租户时要把该租户所有会话删掉（和「停用用户即踢会话」同一个手法，现成的）。

### 8.3 唯一冲突的友好提示会**全部失效**

`repo.IsUniqueViolation(err, "uk_users_username")` 是**按索引名精确匹配**的。
§2.2 要把这些索引全部重建成带 `tenant_id` 的版本 —— **名字一变，所有翻译就都不匹配了**，
用户看到的从「这个用户名已经被占用」退化成一个通用 500。

编译期查不出来（那是字符串常量）。**改索引名时必须 grep 一遍所有
`IsUniqueViolation` 的调用点**，并且每个模块要有一条「重复插入返回友好错误」的测试。

### 8.4 现有索引都缺 `tenant_id` 前缀

每条列表查询现在都会带 `tenant_id = ?`。现有的索引（按 `status`、按 `created_at` 等）
都没有这个前缀，租户一多，每次查询都要先扫出一大堆别人的行再过滤。

**所有列表查询用到的索引都要把 `tenant_id` 放在最前面。** 现在数据量小看不出来，
等三位数租户之后再改就要停机建索引了。

### 8.5 Casbin 的全量 reload 不扩展

现在任何一次角色改动都会**整体重建 enforcer**（`Reload` 换掉整个对象）。
100 个租户之后，A 公司改一个角色会重算所有公司的策略。

现在不用优化，但要记着阈值 —— 真慢了就改成「按租户一个 enforcer + LRU」。

### 8.6 开租户是一个多步写包，必须在一个事务里

建租户 → 建它的内置 admin 角色 → 建角色权限 → 建第一个管理员用户。
中间任何一步失败都会留下一个半残的租户（有租户没管理员，客户登不进去）。
`repo.InTx` 现成的，别忘了用。

## 9. 这一轮通读全文才发现的

前面几轮是「查代码」「模拟运行」，这一轮是**把文档从头读到尾**，找自相矛盾和没写到的。

### 9.1 `tenants.code` 的规则一个字都没定

它要出现在登录框里、将来可能出现在域名里，规则必须先定死：

- **大小写不敏感**（用户不会记得是 `ACME` 还是 `acme`）—— 存小写，唯一索引建在 `lower(code)` 上
- **字符集**：只允许小写字母、数字、中划线；不允许下划线和点（将来做子域名时它们是麻烦）
- ⚠️ **保留字必须拦**：`platform`、`admin`、`api`、`www`、`app`、`static`、`健康检查路径`……
  不拦的话，一个客户注册成 `platform`，将来做子域名就直接撞上平台端
- 长度 2–32

### 9.2 平台登录是整个系统最高价值的攻击目标，方案里没提防护

拿到一个平台管理员账号 = 所有租户的数据。而现在方案对它的要求和普通用户一样。

至少要做到：**平台登录单独限流**（比租户登录更严）、**平台管理员强制强密码**
（不吃租户级密码策略，走平台级的）、**平台管理员的每一个动作都进审计**。

二次验证（TOTP）这一轮不做，但**要记成明确的欠账**，不是忘了。

**✅ 已记在 DECISIONS.md §6** 那句「不做 TOTP」的正下方 —— 记在那里是因为
那句话本身有歧义：租户用户不做 TOTP 是用户明确选择，
而平台管理员不是同一个风险层级（一个账号 = 所有租户的数据），它是欠账。

### 9.3 租户只停用、不删除

§6 只写了开通/停用/启用，没说删除 —— 这是**有意的**，写下来免得以后有人补一个删除按钮：

**不做硬删除。** 停用即可，数据保留。理由：审计链的完整性、误删无法恢复、
以及「客户过两个月又回来了」这种事很常见。真要彻底删（合规要求），
走一次性脚本 + 人工确认，不做成界面上的按钮。

### 9.4 `settings` 改主键会牵动 NOTIFY 触发器

配置是「写库 → 触发器 NOTIFY → 所有实例刷新缓存」（DECISIONS.md §5）。
主键从 `key` 变成 `(tenant_id, key)` 之后，**NOTIFY 的负载里要带上 `tenant_id`**，
否则一个租户改配置会让所有实例把**所有租户**的缓存全刷一遍。

### 9.5 `internal/repo/internal/sqlcgen/` 会撞上目录结构检查

§1.2 ① 要把 sqlc 生成物挪进一层 `internal` 子包。但 `make lint-structure`
有一份 internal 包白名单（DECISIONS.md §1.1），加一层子包会**直接报错**。

实施第 ② 步时要**同时**更新 `lintstructure.go` 的白名单和 §1.1 的目录说明 ——
这是那种「改了 A 忘了同步 B」的典型（MEMORY.md 记过）。

### 9.6 `ForTenant` 和 `InTx` 怎么配合，要先设计

现在事务是 `repo.InTx(ctx, db, q, func(q *Queries) error {...})`，传的是裸 `*Queries`。
包装之后business 代码拿到的是租户绑定的句柄，**事务里那个 `q` 也必须是租户绑定的**，
否则事务内部就绕过了强制机制 —— 而多步写包（开租户、改角色权限）恰恰都在事务里。

签名大概是 `q.InTx(ctx, func(q TenantQueries) error {...})`，第 ② 步要一并定下来。

### 9.7 API Key 认证失败时，审计记在哪个租户

§7.1 定了「公司代码有效、密码错误」的登录失败记在那个租户名下。
**API Key 同理**：key 有效但被停用 → 记在它所属租户；key 根本不存在 → 记 NULL。
别漏了这一半。

### 9.8 复合外键：六条还是两条？—— 全都改

§2.2.1 写「六条全部改」，而实施顺序里一度只写了「两条」。**统一成全都改。**

⚠️ 实际数下来是**七条**（表里那六行中 `user_roles` 占两条），实现时按七条做的。

理由：成本是固定的（每个被引用表加一个 `(tenant_id, id)` 唯一索引），
而「只保护危险的两条」意味着以后每加一条外键都要重新判断一次「这条危不危险」——
判断题比照抄贵得多，而且总有一次会判错。


## 10. 以外部安全评审的视角再读一遍

换个身份：假设是第一次看到这份方案的安全评审，会问什么、会挑出什么。
上面的 §9 是「作者通读找矛盾」，这一节是「外人拿着代码找洞」，查法不同，结果也不同。

### 10.1 🔴 平台管理员的会话无处安放

`sessions.user_id` 是 `NOT NULL REFERENCES users (id)`。而平台管理员在
`platform_admins` 表里（§2.3）—— **它们的会话根本插不进 `sessions`**。

方案里一个字没提这件事，而它会在实施第 ⑤ 步时当场卡住。三个选项：

| 选项 | 评价 |
|---|---|
| 单独一张 `platform_sessions` | ✅ **推荐**。两套主体本来就该有两套会话，cookie 名也该分开 |
| `sessions.user_id` 改成可空 + 加 `platform_admin_id` | 多态外键，两列互斥要靠 CHECK，查询处处要判，容易漏 |
| 把平台管理员塞回 `users` | ❌ 直接推翻 §2.3，`users.tenant_id` 又得可空 |

**顺带**：两套 cookie 名要不同，否则平台管理员和租户用户在同一浏览器里会互相踢掉。

### 10.2 🔴 `sessions.tenant_id` 是第二份真相

租户本来可以从 `user_id` 推出来（`users.tenant_id`）。在 `sessions` 上再存一份，
就有了**两份可能漂移的安全关键数据** —— 而整套隔离都以「会话里的租户」为唯一来源（§4.2）。
一旦漂了，就是拿着 A 的身份读 B 的数据。

好在 §2.2.1 那六条复合外键里正好有 `sessions.user_id`：写成
`FOREIGN KEY (tenant_id, user_id) REFERENCES users (tenant_id, id)` 之后，
**数据库保证这两份永远一致**。⚠️ 但文档没说这是它的作用之一 —— 实施时如果有人觉得
「sessions 加复合外键没必要」把它砍了，这个洞就开了。**这条外键是安全约束，不是洁癖。**

### 10.3 `audit_chain_head` 的主键不能是可空的 `tenant_id`

§2.4 说哈希链按租户各一条，主键换成 `tenant_id`。但 §7.1 又说
`audit_logs.tenant_id` **可空**（未认证请求）。**NULL 做不了主键**，
那平台级审计（`tenant_id IS NULL` 的那批）的链头放哪？

要么给平台级事件一个哨兵租户 ID（比如全零 UUID），要么 `audit_chain_head` 用
`coalesce(tenant_id, '000...')` 做主键。**实施前必须定，否则触发器写不出来。**

### 10.4 `MustTenant` 白名单 ≠ 没人把守

§6 说 `/platform` 要进 `MustTenant` 的白名单。**白名单的意思是「跳过租户检查」，
不是「跳过所有检查」** —— 必须同时明确：

- `/platform/*` **必须要求平台管理员主体**，拿租户用户的会话打过来要 403
- 反过来，拿平台管理员的会话打租户接口也要拒绝

白名单是最容易开出洞的地方。**每加一条白名单，都要写清楚「跳过了什么、由谁接手」。**

### 10.5 租户级设置需要平台强制的上下界

§7.2 把密码策略、会话超时改成租户级。那么**租户管理员可以把密码策略调到 1 位、
会话超时调到一年** —— 他给自己公司挖坑，但出了事是平台的品牌在承担。

平台级设置里要有**下限**（最短密码长度、最长会话时长），租户只能在区间内调。
这是 SaaS 的常规做法，现在不写将来会忘。

**✅ 已落地**（迁移 00011 + `internal/config/bounds.go`）。区间存在 `platform_settings`
里，键名 `limits.<租户级 key>.min` / `.max` —— 不是代码里的常量，
所以接了合规要求更高的客户时平台整体收紧一档，不用发版。
没有对应 `limits` 行的 key 不受限，想限就加一行。

护栏在 `Settings.Set` 上，那是租户级配置**唯一的**写入口：
将来配置管理页面接上来时自动受保护，那个页面不用记得自己校验一遍。

### 10.6 幂等键带了租户仍然不够

§3.2 ⑦ 说幂等键的 map key 要带租户。但键是**客户端自己传的字符串** ——
同一个租户内，A 用户和 B 用户撞上同一个 key，B 会直接拿到 A 那次请求的结果。

**键应该是 `(租户, 主体, 客户端给的 key)`。** 租户维度只解决了跨租户干扰，
租户内的用户之间同样要隔开。

### 10.7 递归 CTE 的**递归部分**没有租户条件

部门取子树的查询（`department.sql`）长这样：

```sql
WITH RECURSIVE subtree AS (
    SELECT d.id FROM departments d WHERE d.id = $1 AND d.deleted_at IS NULL
    UNION ALL
    SELECT d.id FROM departments d JOIN subtree s ON d.parent_id = s.node_id   -- ← 这里没有租户条件
    WHERE d.deleted_at IS NULL
)
```

种子那半会带上 `tenant_id`，但**递归那半只靠 `parent_id` 关联**。
复合外键保证了不会有跨租户的父子关系，所以实际泄不了 —— 但：

1. **纵深防御**：递归部分也该显式带 `AND d.tenant_id = $2`，不依赖另一个约束的正确性
2. **§1.2 ③ 的静态检查会拦下它** —— 而这正好说明那个检查有用。
   ⚠️ 别图省事把整条查询加进豁免白名单：**豁免的粒度是表，不是查询**，
   为一条查询开豁免会开出无数条

### 10.8 跨租户测试只测了「读」

§1.2 ④ 说「调 List/Get，断言看不到对方的」。**写入没测。**

必须同时断言：拿 A 的租户上下文去 `Update` / `Delete` 一个**属于 B 的 id**，
影响行数必须是 0。这是最容易漏的一类 —— 读的时候大家都记得加条件，
按 id 更新时很容易觉得「id 是唯一的，够了」。

### 10.9 「默认租户」会变成一个真实可登录的租户

§7.5 说迁移时建一个默认租户回填现有数据。那它的 `code` 是什么？
如果是 `default` 这种，部署到公网后就是一个**任何人都能猜到公司代码的真实租户**。

要么给它一个随机 code，要么迁移完就把它停用。**别让开发期的产物变成生产上的入口。**

### 10.10 平台管理员的引导：第一个平台管理员从哪来

§5 讲了租户怎么开通，但**平台管理员自己怎么产生**没写。现有的
`auth/bootstrap.go` 是给单租户的首个管理员用的，多租户下它要变成
「首个**平台**管理员」。

这条链路是整个系统权限的源头，要和现有 bootstrap 一样：随机密码、只显示一次、
强制首次登录改密，而且**只在库里一个平台管理员都没有时才允许跑**。

### 10.11 我作为评审还会追问的三件事

- **「租户」和「组织」在文案里要统一。** 现在文档里两个词混用，界面上再混就更乱。
  建议对用户一律叫「组织」，代码里一律叫 `tenant`。
- **停用租户之后，它的数据还在库里，谁能看？** 平台管理员能看是合理的，
  但要明确写出来，并且这类访问要审计。
- **审计能不能证明「平台管理员没看过我的数据」？** 现在平台端不碰业务表（§6），
  所以答案是「结构上就没有这条路」—— 这是个很好的性质，**应该在文档里明说**，
  它是将来跟客户解释隔离时最有力的一句话。


## 11. 攻击者视角：拿 OWASP 的清单打一遍

OWASP 有一份 [Multi Tenant Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Multi_Tenant_Security_Cheat_Sheet.html)，
而**跨租户越权在 OWASP API Top 10 里是 API1:2023（BOLA），排第一位**。
渗透测试找跨租户漏洞的标准手法是：拿两个租户的账号，用 A 的身份去够 B 的东西，
挨个试**对象 ID、API 参数、导出、邀请、搜索、报表、后台任务、管理功能**。

按这张清单打一遍我们的方案：

### 11.1 🔴 「按 id 查一行」必须是复合条件 —— 这是 BOLA 的正面

OWASP 原话：**"Use composite keys (tenant_id + resource_id) for all lookups"**。

`GetUser(id)` 这类查询很容易只按主键查 —— 「id 是 UUID，全局唯一，够了吧」。
**不够。** 拿到别租户的一个 id（从日志、从截图、从离职员工那里）就能直接读到那条记录。

**硬规矩：所有按 id 的查询都必须是 `WHERE id = $1 AND tenant_id = $2`。**
§1.2 ① 的包装层要覆盖它，§1.2 ③ 的静态检查也要覆盖它 ——
后者尤其重要，因为「按主键查」看起来最无辜，最容易被判成不需要租户条件。

### 11.2 跨租户访问要表现成「不存在」，不是「无权限」

用 A 的身份访问 B 的资源，返回 403 和返回 404 是两回事：
**403 等于承认「这个 id 是存在的，只是不属于你」** —— 那就是一个存在性 oracle，
攻击者可以用它枚举出别租户有多少数据、id 长什么样。

**一律返回 404**，和「这个 id 压根不存在」完全一致。既有的 `errs.NotFound` 就够用。

### 11.3 外键报错会泄露「那个 id 存在」

建用户时传一个**别租户的 `department_id`**：复合外键（§2.2.1）会拦下来 ——
这是对的，但**报错信息不能原样返回**。数据库的外键冲突信息会说明是哪个约束、
哪个值，等于确认了「那个部门 id 是存在的」。

要在 repo 层翻译成通用的「部门不存在」，和真的不存在给一样的回应。
现有的 `repo.IsUniqueViolation` 是这套翻译的雏形，外键冲突也要照做一份。

### 11.4 批量操作的返回值 —— 现有代码是对的，别改坏

「把这些人加入部门」传的是一组 user_id。**如果返回值按「传入了几个」算，
那传一堆别租户的 id 进去，返回数字就会告诉你有几个是真实存在的。**

查过了：`addMembers` 返回的是 `Affected`，来自 SQL 的**真实影响行数**，
跨租户 id 会算 0。**这条现在是对的，加租户条件时别改成按输入长度算。**

### 11.5 前端缓存跨租户残留

React Query 的缓存挂在浏览器里。**同一个浏览器换一个租户的账号登录**，
如果不清缓存，上一个租户的列表数据还在。

现有代码在**登出**时有 `queryClient.clear()`，但换账号不一定先登出（直接去登录页覆盖会话）。
**登录成功时也要 `clear()`** —— 这条和 MEMORY.md 里「登录成功后必须先刷 /me 再跳页」
是同一个位置的事，一起做。

### 11.6 `tenants.code` 人可猜，这是和 OWASP 的一处**明知故犯**

OWASP 说 **"Use cryptographically secure, non-guessable identifiers for tenants"**。
而我们的公司代码是 `acme` 这种人能记住、也就能猜到的东西 —— 因为它要出现在登录框里，
不可读就没法用。

**明确记下这个取舍和缓解措施**：

- `code` **只用于登录时定位租户**，其余一切内部引用一律用 UUID
- 登录接口按 IP + 公司代码限流（§3.2 ⑦）
- **不提供任何「校验公司代码是否存在」的接口**（§4.1）
- 三种登录失败的回应和耗时完全一致（§4.1）

做到这四条，「code 可猜」就只是「知道某公司用了我们的产品」，而不是任何数据风险。

### 11.7 UUIDv7 会泄露创建时间

主键是 UUIDv7（DECISIONS.md §2.1），它**前缀带毫秒时间戳且单调递增**。
拿到一个 id 就知道这条记录大概什么时候建的，也能推断出增长速度。

这是 UUIDv7 的已知取舍（换来的是索引局部性），**不改**。
但要知道：id 出现在 URL 里就等于把创建时间也放出去了。

## 12. 运维视角：上线之后怎么发现问题

OWASP 那份清单里有一整节是日志与监控，而我们的方案**一个字都没提** —— 补上。

### 12.1 🔴 所有日志都要带 `tenant_id`

现在的结构化日志带了 `request_id`（DECISIONS.md §4.4）。多租户下**必须再带 `tenant_id`** ——
否则出了问题只能在全量日志里翻，而客户报障时给你的是「我们公司昨天下午打不开」。

放在 slog 的公共字段里，跟着 ctx 走，和 `request_id` 同一个位置注入。

### 12.2 怎么知道「跨租户访问」真的发生了

这是不用 RLS 之后最难受的一点：**没有兜底网，也就没有「被兜住」的信号**。
漏写租户条件的查询会安静地返回别人的数据，没有任何报警。

现实可做的两件事：

1. **审计带上租户**（§7.1 已有），异常模式能事后查 —— 比如同一个会话在短时间内
   访问了大量不同的资源 id
2. **给 `ForTenant` 包装加一个 debug 模式**：非生产环境下，把查回来的行逐条核一遍
   `tenant_id` 是不是等于当前租户，不等就 panic。生产关掉（性能），
   **但集成测试全程开着** —— 这样漏条件的查询在测试里会炸得很响

第 2 条是这个方案里**最接近「兜底网」的东西**，成本很低，强烈建议做。

**✅ 已落地**（`internal/repo/assert.go`）。生成的每个有返回行的 `ForTenant` 方法
都包了一层 `assertTenant`，反射核对每一行的 `tenant_id`，不等就 panic。

三档：**集成测试始终开着**（`testdb.Start` 里翻开，不看配置）、
**staging 用 `server.tenant_assertions: true` 打开**、**生产关掉**。
staging 那一档尤其值钱 —— 那里有接近真实的数据量，
而漏了租户条件的查询在只有一份数据的库里**根本看不出来**（§3.2 ⑧ 那个陷阱）。
开着的时候启动日志会 WARN 一句，免得进程 panic 时没人知道是谁干的。

#### 第二层：核**发出去的 SQL**（`internal/repo/trace.go`）

上面那层核的是**查回来的行**，所以它有两个天生的盲区：

| 盲区 | 为什么 |
|---|---|
| **写操作** | `execrows` 只回一个数字，没有行可核 |
| count 查询 | 一个 int64 里没有租户信息 |

而 §10.8 那类「批量按 id 写」恰恰落在第一个盲区里 —— 也就是 §15.8 审计中发现的、
**五层里有四层看不见**的那一类。

第二层从另一个方向看同一件事：**不看结果，看语句**。接在 pgx 的 `QueryTracer` 上，
那是整个进程里唯一能看见所有 SQL 的位置 —— sqlc 生成的、手写的、动态拼的，一视同仁。
两条规则：

1. **条件在不在** —— 判据来自 `internal/tenantsql`，和 `make lint-sql` 是**同一份实现**
2. **绑的是不是对的那个租户** —— 这条**别的几层都做不到**：条件在、语法对、静态检查也过，
   但拿着 A 的会话去查 B 的数据，只有比对值才看得出来。它守的是 §4.2 那条
   「租户唯一来源是会话」的红线，那条规矩在此之前没有任何机械强制

⚠️ **判据必须和构建期共用一份**，所以它单独成包（`internal/tenantsql`）而不是各写一份。
理由见 §15.8：这个项目已经栽过一次「两个检查看的不是同一件事，中间有缝」。

豁免有两条路，都要求写明理由：sqlc 的查询走**生成出来的**清单（sqlc 会把
`-- tenant-exempt:` 剥掉，标记到不了运行期，只能按查询名对）；手写的 SQL
把标记写在 **SQL 里面**，构建期和运行期认同一行。两条都不命中就是**默认拒绝**。

#### 验证方式

**真往一条查询里植入 bug**：把 `GetUserByID` 的 `WHERE tenant_id = $1`
去掉，重新生成，跨租户测试立刻炸出

> `repo: 跨租户数据泄露 —— ForTenant(...a1) 查回了属于 ...b1 的行（sqlcgen.User）`

——而在这层网装上之前，那条查询会安安静静地成功。

### 12.3 每租户配额，不只是限流

OWASP 建议 **"per-tenant rate limiting and quotas"**。限流管的是瞬时速率，
配额管的是总量（用户数上限、存储上限）。

这一轮不做配额，但**限流一定要按租户分桶**（§3.2 ⑦），
否则一个租户跑个批量导入就能让所有客户变慢。

**✅ 分桶已落地**（§15.8）。只按 IP 限流在 SaaS 下是不够的：一家公司十个人十个 IP，
每人都在自己的额度内，加起来照样能把服务压住，而**别家客户没有任何办法**。
配额（用户数上限、存储上限）仍然不做，等真有付费客户再说。

### 12.4 租户离场：和 OWASP 直接冲突的一条，要正视

§9.3 定了「只停用不删除」。但 OWASP 明确说
**"Ensure complete data deletion on tenant offboarding"、"Don't retain tenant data indefinitely"** ——
GDPR 这类法规里「删除权」是硬要求。

**这个冲突现在可以接受**（还没有真实客户、也没做合规承诺），但要写下来：
真接了要合规的客户，就必须补一条**彻底删除流程**（人工触发 + 二次确认 + 删除后出具凭证）。
现在不做，是因为做半套的删除比不删更糟 —— 留下孤儿数据还以为删干净了。

## 14. 对代码生成器（第 ⑤ 步）的影响

**这就是多租户必须排在生成器前面的原因。** 生成器的模板要固化：

- 每张业务表带 `tenant_id NOT NULL`，**索引以 `tenant_id` 打头**（§8.4）
- 每个唯一约束以 `tenant_id` 打头
- 每条 SQL 都带 `tenant_id` 条件（否则过不了 §1.2 ③ 的静态检查）
- **产出租户绑定的 `Queries` 包装**（§1.2 ①）
- **产出一条两租户的隔离测试**，而且两个租户都要有数据（§3.2 ⑧ 那个陷阱）

生成器先做完再改多租户的话，已经生成的每个模块都要返工一遍。

### 15.3 第二轮：把排期项一并修完，再 review 一遍

| 问题 | 实测 | 修法 |
|---|---|---|
| **停用租户对已登录会话不起作用**（§8.2） | 停用后拿旧 cookie 照样能查数据，只有新登录被挡 —— **看起来生效了，其实客户的人能一直用到 cookie 过期** | 认证时核 `tenants.status`（会话和 API Key 两条路）。在这里查而不是「停用时逐条吊销」：连绕过应用直接改库的停用也照样生效 |
| **幂等键没有租户/主体维度**（§10.6） | 键是 `方法+路由+客户端key`。返回 409 而不是上一次的结果，所以是**跨租户干扰，不是数据泄露** | 键前面加 `(租户, 主体)` |
| **登录只按 IP 限流**（§3.2 ⑦） | 换一批 IP 就能不限次地打同一家公司 | 加公司代码这一维。⚠️ 阈值故意定得很高、窗口只有一分钟 —— 长时间锁死等于把限流变成针对客户的可用性武器 |
| **平台级审计链没有验证入口** | `ForTenant` 拒绝零值，而平台链的键是全零哨兵 | 单独一条 `tenant_id IS NULL` 的查询走 Unscoped，顺带让 `ListAuditChain` 回到能用索引的等值条件 |
| **`lint-sql` 只看 `db/queries/*.sql`** | Go 里手写的裸 SQL 不在覆盖范围 —— 那正是 §1.2 说的「手写代码」缺口 | 扩到 Go 的字符串字面量（用 AST 取，注释里的示例不算）。补上之后立刻查出 2 处测试里的裸 SQL 没带租户条件 |

**修完之后再 review，又抓到两个 —— 其中一个正是前面那条修复引出来的：**

| 严重度 | 问题 | 怎么发现的 |
|---|---|---|
| 🔴 | **停用再启用之后，那家公司的人能登录但每个请求都 403** | 写探针试了一遍「停用 → 启用」。根因：权限策略和配置加载都只取「启用中的租户」，停用时它的策略从内存里消失，**重新启用没有任何东西会触发重载**（`authz_changed` 只挂在角色相关的表上），只能重启服务才恢复。改成遍历**全部**租户 —— 停用的租户认证就过不去，把策略留在内存里没有风险 |
| 🟡 | **被停用时前端静默踢回登录页** | 浏览器实测。再登一次会看到「用户名或密码错误」（登录接口必须那么回，否则成了客户名单探测器），于是整家公司被莫名其妙挡在门外，还以为是自己密码记错了。改成显示「组织已停用」——**这不算泄露**：能走到这一步的人手上有这个组织的有效会话 |

### 15.4 第 ④ 步：权限护栏

④ 里有一半在前面几步就被迫做掉了（配置缓存按租户、幂等键与限流带租户），
剩下的两件：

- **三条兜底护栏按租户**（§3.2 ①）。`CountActiveAdmins` 在 ② 就改成带租户了，
  这一轮补的是**验收测试**：一个租户排除掉自己最后一个 admin 之后数出 0（护栏会拦），
  而且 A 加人**不会**让 B 的护栏跟着松掉。内置 admin 角色每租户各一个，互相看不见也动不了。
- **唯一冲突翻译**（§8.3）。这次是靠「重建索引时刻意沿用原名」躲过去的 ——
  但那是自觉。补了两道：`make lint-sql` 静态核对 `IsUniqueViolation` 引用的索引名
  在迁移里真实存在（改名当场报错），加一条接口层测试确认翻译真的还在生效
  （变异验证过：把索引名改一个字，测试立刻看到 500）。

### 15.5 第 ⑤ 步：平台管理端

验收标准是「开一家新公司并交付给客户」，所以最后是拿浏览器**从头走了一遍**：
平台管理员登录 → 开通「和顺建材 / heshun」→ 拿到一次性凭据 →
换成客户身份登录 → 被要求改密 → 进系统看到自己的组织。这一趟里抓到的问题：

| 严重度 | 问题 | 怎么发现的 |
|---|---|---|
| 🔴 | **同时登着平台端和某个租户时，租户端进不去** | 就是走这一趟撞上的：登录明明返回 200，一进去又被弹回登录页，来回死循环。根因在认证中间件 —— 它按「先看平台 cookie，有就用」挑身份，而**同一浏览器同时登两边是设计上支持的**（§10.1，两套 cookie 名不同就是为了这个）。于是租户请求被认成平台管理员，撞上 Realm 对齐拿到 `perm.denied`，前端认不出这个码，只会把人踢回登录页。改成**按请求路径选会话套**，和 CSRF 那层一样 |
| 🟡 | **平台管理员首次登录改不了密** | 改密接口自己也在「必须改密」的阻断范围里，只能上数据库救。白名单**两套都要列全** |
| 🟡 | **一次性密码里有 `O`/`0` 分不清** | 转抄那一步自己就错了两次。这串东西的宿命是被人念出来、抄进微信、再打进登录框，可辨认比字母表大小重要。挖掉 `0O1lI`，并且三类字符各保证至少一个（客户改密时要求「大小写 + 数字」，发一串纯字母的初始密码等于给人添堵） |

**一处和方案不同**：租户会话打平台接口（以及反过来）现在返回 **401 而不是 403**。
按路径选会话套之后，一边的凭据到了另一边就是「没带」，而不是「带了但不够格」——
401 也确实是更该给的那个：403 等于告诉对方「你的身份我认出来了」，
而且前端拿到 401 会按路径把人送去**对应的**登录页。
§10.4 那条 Realm 对齐没有因此失效，它退到兜底位（防「谁把业务接口注册进了平台路由」），
由 `internal/middleware/realm_test.go` 直接测中间件来守。

**前端两棵子树是分开的**（§10.1），这一轮验证了那个决定是对的：
租户会话的 `<SessionProvider>` 一度挂在应用最外层，结果平台端页面也去查租户的 `/me`，
401 之后人被顶到租户登录页。改成只罩住租户那棵子树。

### 15.6 第 ⑥ 步：收尾

- **日志带 `tenant_id`**（§12.1）。做成 `slog.Handler` 包一层（`httpx.LogHandler`），
  从 ctx 里自动补 `request_id` 和 `tenant_id`，**不只是访问日志** ——
  靠每个调用点自觉写的话，漏掉的恰好会是出事那条。
  写这一条时当场撞了一次自己写的注释：认证有三条路径（平台会话、API Key、租户会话），
  改的时候只改到两条，第三条（租户会话）的缩进不同没被替换。
- **API Key 失败的审计归属**（§9.7）。原来只有「组织已停用」记了租户，
  **key 过期、secret 猜错这两条没记** —— 而 secret 猜错恰恰是最该记的一种：
  有人拿着这个组织的 key 前缀在爆破后半段，被爆破的是客户的对接凭据，
  记成平台级事件的话客户在自己的审计里什么都看不到。改成 prefix 命中即归属。
- **文案**（§7.4）已在前几步做掉（登录页公司代码、侧栏组织名、
  「本组织全部数据」），这一轮是浏览器复查了一遍。
- **模块生成器**（§7.4 最后一行）还没实现，那是脚手架自己的路线图。
  在 `cmd/gen/module.go` 留了记号：实现时模板必须带 `tenant_id`、
  唯一索引 `tenant_id` 打头、每条查询带租户条件。
  生成器一旦吐出不带租户的模板，后面每个模块都从错的地方起步。

### 15.7 六步之后：把方案里剩下的欠账清掉

⑥ 做完之后又过了一遍全文，把「说了要做但不在六步里」的三条补上：

| 条 | 做了什么 |
|---|---|
| §12.2 运行期兜底 | `ForTenant` 查回来的每一行都核一遍 `tenant_id`。**这是整套方案里最接近兜底网的东西**，之前一直没做 |
| §10.5 设置上下界 | 租户管理员原来能把密码策略调到 1 位、锁定时间调到 0 —— 他给自己公司挖坑，出了事是平台的品牌在承担 |
| §9.2 TOTP 欠账 | 记到 DECISIONS.md §6 那句「不做 TOTP」正下方，并说清为什么平台管理员不是同一个风险层级 |

**剩下的都是文档明说不做的**：租户配额（§12.3）、彻底删除流程（§12.4，
和 OWASP 的冲突已写在那里）、以及 §16 那张「明确不做」的表。
模块生成器还没实现，但在 `cmd/gen/module.go` 留了「模板必须是多租户的」这条记号。

**这一轮的一个教训**：`§10.5` 的护栏差点写成只认 `int`。
配置页面接上来之后，值是从 JSON body 里解出来的 —— 那是 `float64`。
只认 `int` 的话，**恰恰是租户改配置的那条路会静默跳过校验**，
而单元测试里传的都是字面量 `int`，全绿。测试里专门钉了一条 `float64` 的用例。

### 15.8 全量安全审计：四处修复，全部落在**检查器本身**

六步做完之后又整体审了一遍（不是照文档打钩，是拿探针去试）。
结论是数据模型和强制机制都对得上文档，**没有找到能实际拿到别家数据的路径**。

但四个问题全在检查器上 —— 而没有 RLS，检查器就是唯一的防线，
它漏判等于那一层不存在，**而且是静默的**：所有查询照样绿。

| 严重度 | 问题 | 怎么发现的 | 修法 |
|---|---|---|---|
| 🔴 | **`lint-sql` 的 `Platform()` 白名单是死代码** —— 提前 return 只判了 `.Unscoped()`，只调 `.Platform()` 的文件整个被跳过。而 `Platform().ListTenants()` 就是整份客户名单（§8.1） | 往 `internal/service/user` 里加一行 `_ = s.store.Platform()`，`make lint-sql` **全绿** | 前置过滤改成两个句柄的并集；两个句柄各配一条「故意违规」的守门测试 |
| 🔴 | **裸的 `tenant_id` 条件会连带放过别的表** —— 一段 SQL 里有裸绑定就把所有不带别名的租户表全算成绑好了 | 探针：`UPDATE users … AND department_id IN (SELECT id FROM departments WHERE tenant_id = $1)` 通过了检查。条件绑的是 departments，users 光着 —— 传一串别家的 user_id 就能把人一起停掉（§10.8 那一类） | 裸绑定只在「这一段只有一处不带别名的租户表引用」时算数，多于一处要求写限定名；两条探针钉成测试用例 |
| 🟡 | **限流没有租户维度**，而 §15 的 ④ 打了勾 | 读代码：`ratelimit.go` 只有 `RealIP()` 一维。真加了租户维度的只有登录节流的公司代码那一档 | 加一个按租户分桶的限流器，挂在 `Authenticate` **之后**（§3.2 ⑦、§12.3） |
| 🟡 | **平台管理员的动作在审计里记成普通 user** —— `ActorPlatform` 只在平台登录那一处用过，开组织/停组织走的是中间件的 else 分支 | 读代码：常量定义了、CHECK 约束放行了，但翻译只有两档 | 翻译改成穷举 switch；四种主体各钉一条用例（§9.2） |

⚠️ **第二条最值得记住，因为它证明了「多层防线」不等于「多层都看得见」。**
那一类跨租户**写**操作，五层里有四层是瞎的：

| 层 | 为什么看不见 |
|---|---|
| ① `ForTenant` 包装 | 查询确实有 `tenant_id` 参数，照样注入，看着完全正常 |
| ② `MustTenant` | 有租户，放行 |
| ③ `lint-sql` | 就是它漏了 |
| §12.2 运行期兜底 | 核的是返回行，**写操作没有返回行可核**（`repo/assert.go` 自己说明了这点） |
| ④ 跨租户测试 | 唯一能拦的一层，但要**有人记得写** |

所以 §10.8 那句「写入也要测」不是补充说明，是**这一类漏法唯一的兜底**。

**这一轮四条修复各配了守门测试，而且都做了变异验证**：把代码改回出问题那版，
对应测试立刻红。检查器自己没有测试的时候，它是最容易腐化的一层 ——
因为它坏掉的表现是「一切正常」。

**回滚**：这六步是一条单向路，做到一半退不回去（表结构、认证链路都变了）。
好在现在**只有本地库**，重建即可 —— 所以要趁没有真实客户数据之前做完。
真上了生产之后再改多租户，成本是现在的几倍。

⚠️ **② 必须紧跟着 ①，而且是整件事里最要紧的一步。** 不用 RLS 就意味着没有兜底网，
②那套机械强制**就是唯一的防线**。先把它立起来，后面每一步才有验收依据；
反过来先写业务、最后补检查的话，中间任何一步漏了租户条件都不会被发现。

## 16. 边界：这些明确不做

划在前面，免得需求一路膨胀：

| 不做 | 理由 |
|---|---|
| 跨租户共享数据（公共模板、共享字典） | 一旦有共享数据，`ForTenant` 就要开例外口子，而每个例外都是一处只能靠自觉的地方 |
| 租户之间迁移/合并数据 | 极低频，真要做就写一次性脚本，不做成功能 |
| 单租户自定义域名 | 要泛域名证书 + 路由，收益只是好看 |
| 按租户定制字段 / 定制表单 | 那是低代码平台，不是这个脚手架的定位 |
| 按租户计费 / 用量统计 | 等真有付费客户再说 |
| 租户级数据导出 | 短板已知（§1），等客户提再写导出任务 |

**推后但会做**：自助注册（等发信能力）、平台端的用量看板。
